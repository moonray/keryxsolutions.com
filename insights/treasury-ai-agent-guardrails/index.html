How do companies keep AI agents from taking the wrong action in treasury workflows?

By treating autonomy as something the agent earns in tiers, not a setting it ships with. Treasury actions move money and are often irreversible, so the working pattern is: read-only by default, credentials scoped to the narrowest useful grant, hard limits on size and frequency, and a human approval gate on anything that crosses a threshold. The agent plans; the stack decides what the plan is allowed to touch.

Tiered autonomy, not a yes-or-no question

The failure pattern is treating "can we trust the agent" as one decision. In practice it is a ladder, and treasury teams that run agents safely climb it deliberately:

  • Tier one, read and analyze: the agent sees positions, rates, and obligations, and writes nothing. Almost all the analytical value, a fraction of the risk.
  • Tier two, draft but do not execute: the agent prepares payments, transfers, or reconciliations as reviewed proposals. A human clicks the button.
  • Tier three, bounded execution: the agent executes within hard limits, per counterparty and per day, with everything reconciled after the fact.

Most treasury work that benefits from agents lives comfortably at tiers one and two for a long time. Tier three is earned with a track record, not granted at setup.

Least privilege, mechanically enforced

Scope credentials to the action, not to the role. An agent that prepares vendor payments does not need the wire credentials; it needs access to the payment queue, and the queue's approval workflow does the rest. If the credential cannot move money, no amount of agent confusion can either. That single property does more for safety than any instruction in the prompt.

Limits and approval gates

Hard limits belong in the systems the agent calls, not in the agent's instructions. Instruction-followed limits bend under persuasion; API-enforced limits do not. The working shape: thresholds that trigger human review, per-action caps, and an outright block on classes of action the agent should never take, regardless of how confident its reasoning sounds.

Catching what prevention misses

Guardrails prevent; you still need detection for what slips through. The same outcome checks that catch an off-track workflow apply here: every consequential action verified against intent after it runs. Money that has left the bank cannot be rolled back, so cross-system movements get idempotency keys and reconciliation, not the all-or-nothing of the transactional database updates pattern.

What this looks like day to day

The agent reconciles positions overnight and flags variances at tier one. It drafts the settlement proposals and queues them at tier two. A person approves the queue in one pass in the morning. Nothing about this is a demo; it is the arrangement that lets treasury teams take the productivity of agents without betting the balance sheet on prompt compliance.
