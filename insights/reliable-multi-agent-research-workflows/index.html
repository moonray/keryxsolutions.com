What setup patterns keep multi-agent research workflows from breaking midway?

The pattern that holds up is deterministic orchestration around probabilistic agents. One orchestrator owns the plan and the state. Each delegated step gets a bounded, verifiable task with its own deadline and attempt budget. The workflow advances only when the returned evidence checks out, and progress persists at step boundaries so a failed run resumes instead of restarting. Reliability comes from that structure, not from a smarter model.

Why they break midway

Most mid-workflow failures are not model failures. They are structural ones: an orchestration loop that assumes every delegated call returns in a reasonable time, sub-agents holding state no one owns, steps that pile on top of results nobody checked, and runs that die silently while their status still says running. Swap in a better model and these failures come back, because the structure produced them.

One owner of the plan and the state

A single orchestrator plans, dispatches, and verifies. Agents talk to the orchestrator, not to each other. Peer-to-peer agent chatter is where runs deadlock or diverge: two agents each assuming the other holds the truth. With one owner, the state of the whole run is answerable in one place, at any moment, by design.

Bounded, verifiable delegation

Every delegated task gets three things before it starts: a deadline, an attempt cap, and a deliverable that can be checked mechanically. The deliverable is the key one. "Research this topic" is unverifiable; "return the five sources with the claim each supports" is checkable. A bounded task that misses its deadline stops and reports, instead of drifting.

Verify returns before building on them

Treat every sub-agent report as a claim, not a fact. Spot-check the load-bearing parts: the sources exist, the numbers are where the report says they are, the summary matches the underlying content. A workflow that verifies before it depends is slower per step and dramatically faster per outcome, because it does not spend the second half of the run amplifying a fabrication from the first half.

Checkpoints, resume, and failure discipline

  • Persist progress at step boundaries. A failed run resumes from the last checkpoint instead of repeating finished work.
  • Classify failures before retrying. A deterministic failure (bad input, rejected call) retried unchanged fails again; fix the payload or change the route. Only transient failures get the retry.
  • Watch for silent death: a session that stays labeled running while producing nothing. When freshness cannot be established, corroborate through an independent source before concluding anything is progressing.
  • Cap recovery. After the budget is spent, stop and surface the failure to a human instead of looping the same dead path.

Two adjacent patterns complete the picture: detecting off-track runs early and versioning agents safely, so changes do not reintroduce the failures you fixed. The control-plane argument behind this structure is laid out in full in Why your AI agents keep breaking on the blog.
